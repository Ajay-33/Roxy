# T-0409: Owner-authenticated notification timeline/dashboard

- Status: done
- Phase: 4.2 / Automatic collection and owner dashboard integration
- Estimate: 1–4 hours
- Depends on: T-0408

## Goal

Show the paired owner a real, privacy-safe notification activity count and recent timeline from the hosted metadata read model, with visible unavailable/error states.

## In scope

- Add an Android authenticated reader for the existing notification-summary endpoint, using the encrypted pairing store only.
- Render a user-initiated notification count/recent metadata card in the owner app.
- Make loading, unpaired, empty, and safe error states visible.
- Resolve notification package labels only at local render time; do not persist or log them.
- Add deterministic parser/state tests using synthetic data.

## Out of scope

- Notification text upload, web owner authentication, new collection permissions, changing the automatic write/sync path, or removing diagnostic controls (T-0413/T-0415).

## Acceptance checks

- [x] Automated: valid synthetic summary parses deterministically; malformed/unauthorized responses show safe errors.
- [x] Automated: Android test/build passes and no credential/payload is logged.
- [x] Manual: paired phone reads hosted count/timeline with an empty/offline/error state that remains understandable.
- [x] Privacy/battery: owner-initiated read only; no text, secrets, or app labels leave the device through this feature.

## Battery note

- Expected callbacks/queries per day: zero background queries; one HTTPS request per owner refresh.
- Expected rows and upload bytes per day: no new writes or uploads; small bounded JSON response per refresh.
- Location/foreground service/wake lock impact: none.
- Required physical-phone measurement: confirm refresh does not schedule background work; no multi-day drain attribution required for this UI-only read.

## Privacy note

- Data classes touched: existing private notification metadata (package identifier, digest, kind, time/timezone, redaction count) returned only to the paired app.
- Redaction/retention impact: no text read, rendered, stored, or uploaded.
- New permission or secret: none; existing credential remains Android Keystore-protected.

## Implementation notes

The normal owner UI must never ask for or store the pairing credential outside `PairingStore`. This task uses the existing protected `/v1/notifications/summary` endpoint and does not make the browser dashboard live.
