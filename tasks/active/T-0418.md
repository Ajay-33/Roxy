# T-0418: Notification lifecycle accounting

- Status: active (planned; implementation not started)
- Phase: 4.3 / Notification intelligence and dashboard experience
- Depends on: T-0417

## Goal

Repair the notification event model so Roxy can truthfully distinguish a distinct notification object, a later update to that object, and its removal. The model must never label notification events or updates as individual chat messages.

## Read first

- `docs/PRIVACY-SECURITY.md`
- `docs/BATTERY.md`
- Notification listener, metadata entity/DAO, Room migrations, sync contract, hosted event store, and Phase 4 tests.

## In scope

- Metadata-only lifecycle identity and deterministic event semantics.
- Room migration and documented rollback notes.
- Contract/server compatibility and idempotency review.
- Synthetic unit/integration fixtures for one notification, repeated updates, group summaries, removals, and retries.
- Owner-visible wording that says notification activity/updates, never message count.

## Out of scope

- Notification title/body/sender/contact data, notification extras, app-specific message parsing, global tap collection, keystroke capture, Accessibility access, visual dashboard redesign, or new collectors.

## Acceptance checks

- [ ] A posted object, its updates, and its removal have explicit deterministic handling without double-counting retries.
- [ ] Group summaries remain excluded and no event is presented as a message count.
- [ ] Migration, rollback note, contract tests, Android tests, and server checks pass.
- [ ] Paired-phone validation records aggregate counts only; no notification content or owner app labels enter logs, fixtures, screenshots, or commits.
- [ ] Privacy/battery check: callback-driven only; no polling, foreground service, wake lock, or direct collector network calls.

## Expected resource envelope

- Expected callbacks: unchanged; Android notification callbacks only.
- Expected local rows: at most one lifecycle record per accepted callback, subject to deterministic deduplication.
- Expected uploaded bytes: small metadata envelopes only; no content fields.
- Location / foreground service / wake lock: none.
